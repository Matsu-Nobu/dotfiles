# コードコメント

このファイルの規則は、 プログラムコード内のコメント (`//`, `#`, `/* */` 等で書く注釈) を書く際に適用する。

## 書いて良いコメント

「コードからは読み取れない WHY」かつ「将来も陳腐化しない」の両方を満たすものに限る。 具体的には次の 4 種類のみ。

- **コード外の制約 (言語・FW・API・プロトコル・OS の仕様)**: 例「`stopTimeout 120` は ECS Fargate の task 停止猶予の上限。 これを超えると SIGKILL が飛ぶ」。 コードからは読み取れず、 上流仕様が変わらない限り陳腐化しない情報。
- **意図的に普通でないことをしている理由**: 例「ここで再 connect しているのは、 接続プールの idle timeout が上流プロキシのそれより短いため」。 標準的なコードから逸脱しているなら、 なぜ逸脱したかの理由が必要。
- **危険な前提・不変条件**: 例「呼び出し前に X のロックが取得されていなければデータ破壊が発生する」。 知らずに触ると地雷を踏む情報。
- **微妙な副作用**: 例「この `sleep` は DNS 伝播待ち。 削ると次の read で stale な値を引く」。 削ったときに何が壊れるかが直感的に分からない場合の補足。

## 書いてはいけないコメント

次のいずれかに該当するものは書かない。 これらは PR description / コミットメッセージ / git log の領分。

- **コードを読めば分かる WHAT**: 関数名・変数名・処理内容そのものを言い換えるだけのコメント。
- **PR / Issue / Phase 番号への参照**: 「PR #123 で追加」「Phase 1 採用項目」「Step 2 で〜」など、 開発時のコンテキスト。
- **改修履歴・経緯**: 「初版より集約」「再レビューで指摘されたため修正」「v9-production-safe」など。
- **verify 結果や状況依存の事実**: 「現行 DB スキーマは X」「本番稼働実績あり」「現行 config は null」「実測では最大 72 画素ぶん足りない」「およそ 1.9 秒で最初の文字が出る」など。 検証時点の状態は将来変わるので嘘になる。 自分で測った性能値も、 測った環境の性質であってコードの性質ではない。 仕様として決まっている上限値・既定値は書いてよく、 区別は「上流の仕様が変わらない限り成り立つか」で切る。
- **他リポへの参照**: 「リポ A の B と完全一致」「リポ C の D.tf 準拠」など。 相手側が変わったら成立しない。
- **「念のため」「将来の参考に」「verify 済」「実績あり」のような保険記述**: 必要な根拠を欠いた装飾。
- **レビュー応答**: 「指摘を受けて〜」「再レビューで〜」「初版より〜」など。

## 書き方

- 一行一文。 `#` / `//` の 1 行には 1 文だけを書く。 長い一文は短い複数の文に割り、 文の途中で行を折り返さない。 一行に複数文を詰めるのも、 一文を複数行に流し込むのも、 どちらも読み手に文の切れ目を探させる。
- 造語と内輪の言い回しを使わない。 名詞を連結した造語 (英語の略記 pub、 per-req や、 日本語の複合名詞「機能トグル検査」「会話認可」「空会話作成」) は、 読み手に意味の再構築を強いる。 書き手の頭の中の図を前提にした動詞 (「上へ通す」「握る」「下の層へ渡す」) も同じく禁じる。 「上」が呼び出し元なのか外側の rescue なのかはコードから決まらない。 どちらも動詞を含む普通の文に開き、 何が何にどうなるかを書く (「機能トグル検査は会話認可より先に行う」 ではなく 「アップロード機能が有効かどうかは、 会話がこのセッションのものかより先に確認する」)。 名詞化は書き手の圧縮であって読み手の語彙ではない。
- 想定読者の技術層で一般に流通している技術用語 (focus trap、 display、 WAF、 オフセット、 ポーリング、 ストリーミング等) は、 言い換えずにその語を使う。 説明的に言い換えると平易になったように見えて、 読者が既に持っている辞書を捨てさせる。 造語を禁じる規則は私的な語を対象にしたものであって、 業界標準語には及ばない。 判断は、 公式ドキュメントや一般的な解説記事にその語が出てくるかで切る。 一方、 自分がその会話・その PR の中で発明した語は、 定義済みのつもりでも読者には未定義語である。
- コメントを書く目的は、ユーザーや、共同開発者に意図を説明するためである。コメントの記述内容についても、`~/.claude/CLAUDE.md` の「説明の原則」に従う。

## 判定基準

書く前に 2 つ自問する。 (1) 6 か月後にこのコードだけ読んだ人にこのコメントは意味があるか。 (2) これは PR description / コミットメッセージ / git log に置けないか。 (2) で「置ける」なら必ずそちらに置き、 コードには書かない。

書いたあとは、 対象を知らない読者として先頭から読み直す。 禁止語を検索しても、 「その語がその位置でまだ説明されていない」 ことは見つからない。 意味の確定しない語で止まらないか、 同じ差分の中に同じ語が別の意味で出ていないか (呼び出し関係の「上」と画面をスクロールする「上」など) を、 読んで確かめる。

内部識別子 (変数名・定数名等) の私的な略語は開発者向けとして許容するが、 コメントには `~/.claude/CLAUDE.md` の「説明の原則」の語彙規則を適用し、 ユーザーの目に触れる文言 (エラー / ラベル / aria-label) へ流用してはならない。

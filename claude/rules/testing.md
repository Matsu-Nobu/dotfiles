# テスト

このファイルの規則は、 自動テストを書く・直すときに適用する。 言語やフレームワークに依存しない粒度で書いてあり、 スタック固有の書き方はプロジェクト側の規約が持つ。 同じ観点の定義がプロジェクト側にあればそちらを使い、 無ければこのファイルの記述に従う。

## テストの構造は対象に沿わせる

テストは、テスト対象の構造に沿って置く。 クラスの spec ならメソッドごとに区切り、 その中を条件ごとに分ける。 既にその区切りがあるなら、 新しい検証はそこへ加える。

今回追加した機能の名前で区切りを作り、 複数のメソッドの検証をその下にまとめてはならない。 変更の単位で区切ると、 ファイルの中に「対象で分けた区切り」と「変更で分けた区切り」が混在し、 次に同じ場所を触る人がどちらに足すか判断できなくなる。 追加を重ねるほど、 同じメソッドの検証がファイル内に散る。

判定は「半年後にこのメソッドの挙動を知りたい人が、 一箇所を読めば済むか」で行う。 散っているなら構造が壊れている。

複数の対象にまたがる挙動を確かめたい場合は、 単体の spec に横断的な区切りを作るのではなく、 request spec など対象の粒度が合う場所に置く。

## 準備と実行と検証を分ける

テスト本体には、 実行と検証だけを書く。 テストデータの作成や事前の結線は、 宣言的な準備の場所へ出す。 RSpec なら `it` の中を Act と Assert だけにして、 Arrange は `let` と `before` に置く。 シナリオごとに準備が違うなら `context` を分け、 その直下の `let` と `before` に置く。 実行対象は `subject` にまとめる。

準備が本体に混ざると、 何を実行して何を検証しているのかを読み手が探すことになる。 準備を分離すると、 各テストの主眼が一目で分かる。

判定は「本体に実行と検証以外が書かれていないか」で行う。 準備・実行・検証の順に並んでいるだけでは足りない。

## 内部を偽物に置き換えない

偽物に置き換えてよいのは、 自分たちが挙動を保証できないものだけである。 外部サービスへの通信、 現在時刻、 乱数、 ファイルシステムの副作用が該当する。

自分たちが書いた内部のクラスやメソッドは、 実物を動かす。 権限判定、 モデル、 サービスオブジェクトを偽物にすると、 テストは通るのに本番で壊れる状態を作れてしまう。 特に権限判定を偽物にすると、 判定が呼ばれているかどうかも、 引数の順序が正しいかどうかも検証できなくなる。

準備が面倒だから偽物にする、 という判断をしない。 準備が面倒なこと自体が設計の問題を示している場合が多い。

## 検知できることを確かめる

テストが通ることと、 テストが壊れを検知できることは別である。 検知を確かめずに「テストが通ったので正しい」と報告しない。

新しく検知の仕組みを入れたときは、 その仕組みを一時的に壊してテストが落ちることを確認し、 確認後に元へ戻す。 権限判定を足したなら判定の呼び出しを外す。 所属関係の検証を足したなら絞り込みを外す。 継承や設定の宣言を検知したいなら宣言を消す。

落ちなければ、 テストはその仕組みを検証していない。 通ったという事実だけでは、 テストが何も見ていない可能性を排除できない。

確認したことと結果を報告に含める。 どのテストが落ちたかまで書く。

## 分岐を網羅する

条件分岐を足したら、 その分岐のすべての経路にテストを置く。 条件が複数あるなら、 それぞれが単独で結果を変えることを確かめる。 まとめて 1 つのテストで通すと、 片方の条件が壊れても気づけない。

境界値と異常系を落とさない。 正常系だけのテストは、 期待どおりに動くことしか示さない。

## テスト同士を独立させる

実行順に依存しない。 前のテストが作ったデータや、 前のテストが変えた状態を前提にしない。 単独で実行しても、 順序を入れ替えても、 同じ結果になるようにする。

## 既存のテストを弱めない

既存のテストが落ちたとき、 期待値を書き換えて通す前に、 落ちた理由を確かめる。 実装の変更が正しくてテストの前提が古いなら書き換えてよい。 実装に問題があるなら実装を直す。 テストが検証していた内容を減らして通すことはしない。

フィクスチャを変えて通した場合は、 何をどう変えたか、 それによって検証内容が変わっていないかを報告する。

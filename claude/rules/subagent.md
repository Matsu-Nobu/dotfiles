# 実装作業はサブエージェントを起動して背景で進める

「実装してくれ」 「リファクタしてくれ」 「rebase して」 「mirror endpoint を追加して」 のような、 ファイル編集 + spec 実行 + lint + commit を伴う**実装作業全般**は、 明示的な指示がなくても**サブエージェントを起動して背景で進める**ことを既定動作とする。 ユーザーから「サブエージェントでやって」 と言われるのを待たない。

理由は 2 つ。 一つは、 メインの会話コンテキストを実装の進捗ログで埋めると、 ユーザーが本当に確認したい設計判断や全体状況に対する応答品質が落ちる。 もう一つは、 実装中もユーザーは他の判断 (レビュー、 別 PR の確認、 設計議論) を進められる方が時間効率が良い。

判定の目安: 「自分が verify + 編集 + spec + commit を順に踏む必要がある」 と感じたらサブエージェント候補。 「1〜2 ファイルの数行編集で済む」 「ユーザーへの即時応答が成果物そのもの (= 質問への回答、 説明文)」 はメインで処理。 判断に迷うなら背景で起動する側に倒す。

サブエージェント起動時は `run_in_background: true` を必ず付ける。 メインの会話をブロックしてはいけない。 起動した旨を 1〜2 行でユーザーに伝えてから次の話題に進む。 完了通知で結果報告。 force-push 等のユーザー承認が必要な操作はサブエージェント内で完結させず、 完了報告後にユーザーに承認を求める。


## 流す spec はファイルパスで指示に書く

サブエージェントへの指示には、 最後に流す spec をファイルパスで列挙する。 ディレクトリを指定しない。 範囲を決めさせると関連しそうなものを広く集め、 待ち時間が作業時間を支配する。

挙げるのは変更したファイルに対応する spec だけで、 その呼び出し元や周辺のディレクトリには広げない。 全体が壊れていないかは CI が全件を並列で流して確かめる。

ただし多くの箇所から呼ばれる基盤を変更したときは、 呼び出し元の spec を 1〜2 本だけ代表として加える。 全部を加えるのではなく、 呼び出し元が全滅する類の失敗を CI を待たずに拾うためのもの。

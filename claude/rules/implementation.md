# 実装の規約

## 防御的フォールバックは信頼境界の外側にだけ書く

このルールは「エラーや未定義状態を握って続行する」タイプのフォールバックを禁ずる。 `if defined?(X)`、 `rescue => e; return nil`、 `x = param || default`、 `try` / `method_missing` を使った黙認、 nil ガードで書き潰す形の呼び出し全般が該当する。 書いてよいのは、 信頼境界の外 (untrusted user input / 外部 API レスポンス / ネットワーク / OS 副作用) から入力を受け取る境界の関数だけ。 ここは呼び出し側の挙動をこちらが保証できないので、 fallback で握って生存させるのが正しい。

同じチームの開発者が呼ぶ内部 API や helper の内部にはフォールバックを書かない。 呼び出し規約に違反する呼び方をされたら明示的にエラーで死ぬのが正しい。 理由は三点あり、 テスト環境や CI で契約違反が検出できる (silent に握ると本番まで気付かない)、 fallback が dead code になって読み手の認知負荷を増やす (「どういう条件で undefined になるのか」を毎回考えさせる)、 silent failure の温床になり「実際は壊れているのに正常に見える」状態を作る、 の三つ。

私が過去にやった悪例。 `if defined?(Honeybadger)` を Gemfile に無条件 load されている gem に対して 19 箇所つけて回り、 別のリポジトリの PR でさらに 4 箇所に広げた、 `rescue => e; return nil` で内部エラーを握って上位を欺いた、 パラメータの存在チェックを `|| default` で埋めて type violation を隠した、 など。 「良かれと思って」書くフォールバックは基本的に全部これに該当する。 金輪際やめる。

判定は「これが失敗した場合、 誰の責任か」で切る。 悪意 / 予測不能な入力の失敗ならフォールバック OK (呼び出し側を保護できない)。 内部呼び出しの契約違反は raise で落とす (呼び出し側を教育できる)。

## ユーザーに触れる文言は勝手に確定せず必ず確認を取る

「ユーザーに触れる文言」とは、 エンドユーザーの画面に出る文字列すべてを指す。 フラッシュ / エラーメッセージ、 ボタン・見出し・プレースホルダ等のラベル、 そして aria-label (スクリーンリーダーが読み上げるので可視扱い) を含む。 一方、 例外メッセージ・ログ・特定経路でしか評価されない i18n 値のような内部専用の文字列は、 この規約の対象外として基準を分ける。 ある文字列がどちらかは想像でなく実際のコード経路で確かめる (例: 検証失敗の i18n 文字列が service 層で別の固定文言に変換され、 ユーザーには一切出ないことがある)。

これらの文言を新規作成・変更するときは、 自分の語感で確定させず、 必ずユーザーの確認を経てから確定する (絶対ルール)。 文言は製品・ドメインの判断であり、 IT 屋視点では読者に伝わらない語・体裁・心理的詰まり所を見落とす。 `~/.claude/CLAUDE.md` の「コンプリーテッド・スタッフ・ワーク」に従って推奨案は自分で用意するが、 承認だけは省かず必ず仰ぐ。

書き方の原則。 内部で発明した語彙・略語を可視文字列に使わず、 UI が既に使っている言葉に合わせる (ボタンが「解決」なら「解決判定」のような新名詞を作らない)。 想定読者 (IT に不慣れな事務職) がその語だけで意味を取れることを基準にする。 これは `~/.claude/CLAUDE.md` の「説明の原則」にある「一般に知られている平易な語彙で書き、符号や造語を発明しない」を UI 文言に適用したものである。

エラーメッセージは、 ユーザーが次に取れる実在の行動を示す。 入力欄が無いのに「入力をご確認ください」と促すような、 存在しない操作の指示をしない。 文言は t() 経由で config/locales に置き、 コードへ直接書かない。

## レビューを依頼する前にセルフレビューを完了させる

人間に「レビューしてほしい」「マージしてよいか」「これで完璧か」を問う前に、必ずセルフレビューを完了させてから依頼する。 完了とは、自分で潰せる粗を残していない状態を指す。

セルフレビューが完了したと言えるためには、最低限、次の全てを満たしていなければならない。

- プロジェクトの lint / formatter / 型チェックを実行して、自分の変更範囲で 0 offense
- プロジェクトのテスト suite を実行して、関連する範囲で全 pass
- 変更スコープに対する多角的な再点検 (セキュリティ・互換性・パフォーマンス・テストカバレッジ・命名・コメント・既存資産との重複) を済ませている
- thorough-review skill が存在するなら、それを通している
- 変更が壊しうる前提条件 (本番設定との差・暗黙の規約・他リポとの整合) を grep や CI ログで verify している
- 「これより良い状態は存在しない」と自分で断言できる状態にある

セルフレビューが終わっていないのに「レビュー / マージしてよいか」を聞くのは、人間の時間を「未完成のものを review に出して指摘で戻る」往復に消費させる行為であり禁止する。 syntax check と lint だけで完了とみなしてはならない。

過去に「セルフレビューしていないのに merge お願いと依頼した」事案が複数あり、ユーザーから明示的に強く指摘されたことを踏まえる。 同じ失敗を二度と起こさない。
